13 · 生产化：给模型调用加上边界

前面的代码默认「模型总会很快、总能成功、不会乱花钱」。生产环境不是这样： 模型会慢、会 429、会超时、会失败，还会按 token 计费。这一章按六个边界逐个加固： 超时、重试、限流、降级、成本、安全。

学完这一章，你能做什么

  • 给同步与流式模型分别设置合理超时
  • 只重试值得重试的错误，避免无效重试
  • 在服务入口按租户限流
  • 主模型不可用时做降级
  • 算清 token 成本并守住密钥与工具权限

先理解：模型调用为什么会失控

现象原因边界
请求一直不返回网络卡住 / 模型排队 / 流式无数据超时
偶发失败后恢复429 / 5xx / 网络抖动重试
一个租户打满所有请求没有入口限流并发与限流
主模型故障，全站不可用没有降级主备 / 熔断
账单突然翻倍上下文、topK、输出长度失控成本
密钥泄露、日志带隐私配置与日志没有治理安全

第一步：给同步与流式分别设超时

同步模型的 timeout(...) 同时覆盖连接与读取；不设置时连接默认 15 秒、读取默认 60 秒。 流式模型是另一个类，需要单独设置。 

ChatModel model = OpenAiChatModel.builder()
        .baseUrl("https://api.deepseek.com/v1")
        .apiKey(System.getenv("DEEPSEEK_API_KEY"))
        .modelName("deepseek-chat")
        .timeout(Duration.ofSeconds(90))
        .maxRetries(2)
        .build();
StreamingChatModel streamingModel = OpenAiStreamingChatModel.builder()
        .baseUrl("https://api.deepseek.com/v1")
        .apiKey(System.getenv("DEEPSEEK_API_KEY"))
        .modelName("deepseek-chat")
        .timeout(Duration.ofSeconds(120))
        .build();

流式请求可能长时间没有新 token，读超时要按场景放宽；普通问答的 60 秒不一定够。

第二步：只重试值得重试的错误

maxRetries 默认是 2，即「首次 + 2 次重试」。429 与 5xx 通常可重试； 400、401、403、404 重试没有意义，只会放大延迟与成本。 

ChatModel model = OpenAiChatModel.builder()
        .baseUrl("https://api.deepseek.com/v1")
        .apiKey(System.getenv("DEEPSEEK_API_KEY"))
        .modelName("deepseek-chat")
        .maxRetries(2)
        .build();

工具调用还要考虑幂等：写操作重试前必须确认业务幂等，否则可能重复扣款、重复下单。

第三步：按租户限流，别打满模型

  • 在服务入口按租户 / 用户做令牌桶限流（Bucket4j、Resilience4j 都可以）。
  • 给模型调用与工具调用分别设并发上限，避免工具把线程池占满。
  • 流式连接设置最大生命周期，防止客户端断开后服务端仍长期占用资源。
  • 批量任务走队列，不要在 HTTP 请求里同步跑几十个 Agent。

限流不是模型层的事，而是服务层的事。模型 SDK 不会替你保护整个系统。

第四步：主模型不可用时降级

LangChain4j 没有内置的「自动故障切换」。内置的 RoutingChatModel / RoutingStreamingChatModel 只负责按规则路由， 不会在模型报错时自动切换。需要 failover 时，在外面包一层： 

final class FallbackChatModel implements ChatModel {
    private final ChatModel primary;
    private final ChatModel fallback;

    @Override
    public ChatResponse doChat(ChatRequest request) {
        try {
            return primary.chat(request);
        } catch (RuntimeException e) {
            log.warn("primary failed, fallback", e);
            return fallback.chat(request);
        }
    }
}

生产环境还应加健康检查、熔断与告警；不要在每次失败后都无限降级。 降级模型要能接受同样的消息与参数。

第五步：算清 token 成本

  • 从 ChatResponse.tokenUsage() 取输入/输出 token，按模型单价累计。
  • 用 maxOutputTokens 限制回答长度；长回答是成本大头。
  • 控制 RAG topK 与上下文长度；召回越多，输入 token 越高。
  • 对稳定问题做语义缓存或结果缓存，但注意租户隔离与失效策略。

第六步：密钥、日志与工具权限

  • API Key 只从环境变量或密钥管理服务读取，不进代码、不进镜像、不进日志。
  • 日志默认不记录完整 prompt / completion；需要时按采样与脱敏开关。
  • 工具白名单最小化；MCP 场景用 filterToolNames(...) 收敛工具面。
  • 工具结果视为不可信输入，不要直接拼 SQL、Shell 或 HTML。

上线前检查清单

  1. 超时
    同步、流式分别有上限；流式不沿用短读超时。
  2. 重试
    只重试 429/5xx；写工具确认幂等。
  3. 限流
    入口按租户限流；模型与工具并发分开。
  4. 降级
    主备模型、熔断与告警可演练。
  5. 成本
    token 指标、预算告警、上下文与 topK 有上限。
  6. 安全
    密钥、日志脱敏、工具白名单与最小权限。

常见错误与排查

1. 把所有错误都重试
你会看到
401/400 也重试，延迟翻倍。
因为
没有区分类别。
改成
只对 429/5xx/网络错误重试；401 先修 key。
2. 只设模型超时，不设工具超时
你会看到
一个卡住的工具拖垮请求。
因为
只关注了模型层。
改成
工具执行也要有超时与并发上限。
3. 降级模型不兼容参数
你会看到
切到备用模型后报参数错误。
因为
主模型支持的参数备用模型不支持。
改成
降级前裁剪参数，或统一用最小公共参数集。
4. 日志里有密钥/隐私
你会看到
日志平台出现 sk- 开头的字符串或用户手机号。
因为
全量记录了请求头或 prompt。
改成
统一脱敏；默认只记录摘要。
