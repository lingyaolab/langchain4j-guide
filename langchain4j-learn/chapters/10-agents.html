先说为什么：Agent 不是更复杂的 AI Service

AI Service 解决「一次调用 + 工具循环」；Agentic 解决「多个 Agent 怎么协作」。 它不替代 AI Service，而是在上面加一层共享状态（AgenticScope）与编排器 （sequence / parallel / loop / conditional / supervisor）。

声明式 Agent：@Agent 与 agentBuilder

方法上的 @Agent 表示它可以被其他 Agent 调用；outputKey 决定结果写进共享状态的哪个键。单 Agent 仍然用 agentBuilder 创建。 

public interface Writer {
    @UserMessage("写一个关于 {{topic}} 的三句话故事")
    @Agent(description = "根据主题生成故事", outputKey = "story")
    String write(@V("topic") String topic);
}

Writer writer = AgenticServices.agentBuilder(Writer.class)
        .chatModel(model)
        .build();

AgenticScope：用 outputKey 在 Agent 之间传值

只有设置了 outputKey / typedOutputKey 的 Agent 才会把结果写进 AgenticScope；没设置时结果只出现在调用记录里，不会自动按键保存。 下游 Agent 用 @V("story") 读取同名变量。需要手工读写时，用 readState / writeState。 

UntypedAgent workflow = AgenticServices.sequenceBuilder()
        .subAgents(writer, editor)
        .outputKey("story")
        .build();

var result = workflow.invokeWithAgenticScope(Map.of("topic", "Java"));
AgenticScope scope = result.agenticScope();
String story = (String) scope.readState("story");

顺序工作流：sequenceBuilder

顺序工作流适合「先抽取、再改写、最后汇总」。每个子 Agent 的输出键必须能被下游读到， 通常用 outputKey 显式命名，而不是依赖方法返回值顺序。 

public interface StoryWorkflow {
    @Agent
    String run(@V("topic") String topic, @V("audience") String audience);
}

StoryWorkflow flow = AgenticServices.sequenceBuilder(StoryWorkflow.class)
        .subAgents(writer, editor)
        .outputKey("story")
        .build();

String story = flow.run("虚拟线程", "小学生");

并行工作流：parallelBuilder

并行适合互不依赖的检查：事实核查、风格检查、合规检查可以同时跑。每个子 Agent 必须写不同的 outputKey，最后由一个汇总 Agent 读取这些键。 

UntypedAgent checks = AgenticServices.parallelBuilder()
        .subAgents(factChecker, styleChecker)
        .build();

var result = checks.invokeWithAgenticScope(Map.of("draft", draft));
String facts = (String) result.agenticScope().readState("facts");
String style = (String) result.agenticScope().readState("style");

并行默认不会合并结果，也不会自动写一个汇总键；每个子 Agent 各写自己的 outputKey，需要汇总时再串一个 Agent。

循环与退出条件：loopBuilder

循环适合「生成 → 评审 → 再生成」的迭代。建议同时设置 maxIterations 与 exitCondition：maxIterations 默认是整数上限，只设退出条件才可能无限循环。 

StoryWorkflow flow = AgenticServices.loopBuilder(StoryWorkflow.class)
        .subAgents(writer, editor)
        .maxIterations(3)
        .exitCondition(scope -> ((String) scope.readState("story")).length() < 500)
        .outputKey("story")
        .build();

条件分支：conditionalBuilder

条件分支按 AgenticScope 里的值选择要跑的子 Agent。条件函数只读状态， 不要在里面对模型发请求。 

TriageWorkflow triage = AgenticServices.conditionalBuilder(TriageWorkflow.class)
        .subAgents(scope -> "legal".equals(scope.readState("category")), legalAgent)
        .subAgents(scope -> "medical".equals(scope.readState("category")), medicalAgent)
        .outputKey("answer")
        .build();

Supervisor 与 Planner：什么时候需要

supervisorBuilder 让一个「主管」根据任务选择成员；更复杂的规划模式 （BDI、Blackboard、Debate、Voting 等）在 langchain4j-agentic-patterns 模块。 简单固定流程优先用 sequence / parallel，别一上来就上 Supervisor。

生产化：超时、监听与 HITL

  • 模型与工具超时仍由 ChatModel / 工具执行配置控制，工作流层不替代它们。
  • 用 maxIterations、exitCondition 与监听器给循环加边界。
  • 需要人工审批时用 humanInTheLoopBuilder()，不要自己在业务代码里轮询。
  • 多 Agent 共享 AgenticScope，注意并发写同一个 key 的覆盖问题。

陷阱与窍门

所有 Agent 都写同一个 outputKey

后执行的会覆盖前面的。并行场景尤其明显，每个 Agent 用独立键，再显式汇总。

循环只写 exitCondition 不写 maxIterations

条件可能永远不满足；两个都设，并把退出原因记录下来。

用 Agentic 包装一次普通 chat

单次调用直接用 AI Service 或 ChatModel；编排层会多出状态与调试成本。
