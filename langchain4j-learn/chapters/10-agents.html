10 · Agent 与工作流：从单 Agent 到协作

一个 AI Service 能完成一次任务。真实业务里经常需要「先写、再审、再改」， 或者「同时做事实核查和风格检查」。这一章从单个 Agent 开始，逐步学会用 AgenticScope 传结果，再串行、并行、循环、条件分支，最后判断什么时候才需要 Supervisor。

学完这一章，你能做什么

  • 用 @Agent 把一个 AI Service 声明成可编排的 Agent
  • 用 AgenticScope 与 outputKey 在 Agent 之间传结果
  • 写出顺序、并行、循环、条件四种工作流
  • 知道什么时候该上 Supervisor，什么时候不该

先理解：一个 Agent 不够用时

一个 Agent 适合「一次模型调用 + 工具循环」。当任务需要多个角色协作时，会遇到新问题：

需求单 Agent 的问题工作流
先写初稿，再润色一个 prompt 里塞两个角色，容易互相干扰顺序
事实核查 + 风格检查串行跑两次，慢并行
写到满意为止一次生成可能不达标循环
法律问题走法律专家，技术问题走技术专家一个 Agent 很难同时专精条件分支

Agentic 不替代 AI Service，而是在上面加一层共享状态（AgenticScope）与编排器。

第一步：把一个 AI Service 变成 Agent

给方法加 @Agent，再用 agentBuilder 创建。单 Agent 和上一章的 AI Service 几乎一样： 

public interface Writer {
    @UserMessage("写一个关于 {{topic}} 的三句话故事")
    @Agent(description = "根据主题生成故事", outputKey = "story")
    String write(@V("topic") String topic);
}

Writer writer = AgenticServices.agentBuilder(Writer.class)
        .chatModel(model)
        .build();

@Agent 的 outputKey 决定结果写进共享状态的哪个键。 不设 outputKey 的 Agent 也能被调用，但结果只出现在调用记录里，不会自动按键保存。

第二步：用 AgenticScope 传结果

Agent 之间不直接传参，而是通过共享状态。上游写 outputKey，下游用 @V("story") 读同名变量： 

public interface Editor {
    @UserMessage("把故事改写成适合 {{audience}} 阅读的版本：{{story}}")
    @Agent(description = "按受众改写故事", outputKey = "story")
    String edit(@V("story") String story, @V("audience") String audience);
}

需要手工读取结果时，用 UntypedAgent 的 invokeWithAgenticScope： 

UntypedAgent flow = AgenticServices.sequenceBuilder()
        .subAgents(writer, editor)
        .outputKey("story")
        .build();

var result = flow.invokeWithAgenticScope(Map.of(
        "topic", "一只会写代码的猫",
        "audience", "小学生"));

String story = (String) result.agenticScope().readState("story");

第三步：串起两个 Agent

顺序工作流适合「先写、再改」。每个子 Agent 的输出键必须能被下游读到： 

public interface StoryWorkflow {
    @Agent
    String run(@V("topic") String topic, @V("audience") String audience);
}

StoryWorkflow flow = AgenticServices.sequenceBuilder(StoryWorkflow.class)
        .subAgents(writer, editor)
        .outputKey("story")
        .build();

String story = flow.run("虚拟线程", "小学生");

顺序执行就是按 subAgents 的顺序跑；前一个 Agent 写 story， 后一个 Editor 读 story，再覆盖 story。

AgenticServices.java:187

第四步：并行做独立检查

事实核查和风格检查互不依赖，可以同时跑。每个子 Agent 写不同的 outputKey，最后从 scope 里读： 

UntypedAgent checks = AgenticServices.parallelBuilder()
        .subAgents(factChecker, styleChecker)
        .build();

var result = checks.invokeWithAgenticScope(Map.of("draft", draft));
String facts = (String) result.agenticScope().readState("facts");
String style = (String) result.agenticScope().readState("style");
并行不会自动汇总

并行工作流只负责「同时跑」，不会合并结果，也不会自动写一个汇总键。 需要汇总时，再串一个 Agent 读取这些键。

AgenticServices.java:194

第五步：让 Agent 迭代改进

「写到满意」需要循环。建议同时设置最大轮次和退出条件： 

StoryWorkflow flow = AgenticServices.loopBuilder(StoryWorkflow.class)
        .subAgents(writer, editor)
        .maxIterations(3)
        .exitCondition(scope -> ((String) scope.readState("story")).length() < 500)
        .outputKey("story")
        .build();

maxIterations 默认是整数上限，exitCondition 默认永远为 false。 只设退出条件才可能无限循环；只设最大轮次则一定会在轮次耗尽后停止。

AgenticServices.java:230 LoopAgentServiceImpl.java:24

第六步：按分类走不同分支

先让一个分类 Agent 把问题标成 legal / medical， 再用条件工作流选择分支： 

TriageWorkflow triage = AgenticServices.conditionalBuilder(TriageWorkflow.class)
        .subAgents(scope -> "legal".equals(scope.readState("category")), legalAgent)
        .subAgents(scope -> "medical".equals(scope.readState("category")), medicalAgent)
        .outputKey("answer")
        .build();

条件函数只读 AgenticScope，不要在里面对模型发请求。

第七步：什么时候需要 Supervisor

前面四种工作流都是「你写好结构」。Supervisor 是「让一个主管根据任务动态选成员」： 

SupervisorAgent supervisor = AgenticServices.supervisorBuilder()
        .subAgents(legalAgent, medicalAgent, technicalAgent)
        .build();

它适合成员多、任务类型不确定的场景；固定流程用 sequence / parallel 更可控、更便宜。 更复杂的规划模式（BDI、Blackboard、Debate、Voting）在 langchain4j-agentic-patterns 模块，先不用急着上。

生产化：边界、监听与 HITL

  • 模型/工具超时仍由 ChatModel 与工具执行配置控制，工作流层不替代它们。
  • 循环必须设 maxIterations；并行要控制线程池与超时。
  • 多 Agent 共享 AgenticScope，注意并发写同一个 key 的覆盖问题。
  • 需要人工审批时用 humanInTheLoopBuilder()，不要自己轮询。
  • 用监听器记录每个 Agent 的输入、输出与耗时，不然出问题很难定位。

常见错误与排查

1. 下游 Agent 拿不到上游结果
你会看到
模板变量为空，或直接报变量缺失。
因为
上游没设 outputKey，或下游 @V 名字不一致。
改成
上下游用同一个键；不确定时先 readState 打印 scope。
2. 并行结果全是 null
你会看到
并行跑完，汇总键不存在。
因为
并行不会自动汇总，也没有 Agent 写这个键。
改成
每个子 Agent 写自己的 outputKey，再串一个汇总 Agent。
3. 循环停不下来
你会看到
请求一直不返回，token 持续消耗。
因为
只设了 exitCondition，且一直不满足。
改成
加 maxIterations；退出条件只读 scope，不要发模型请求。
4. 条件分支两个都跑了
你会看到
不该执行的分支也执行了。
因为
两个条件的判断值都为 true。
改成
条件要互斥；分支多时先做分类 Agent，再按分类值选择。

动手练习：内容生产工作流

  1. 写两个 Agent：Writer 生成初稿，Editor 按受众改写。
  2. 用 sequenceBuilder 串起来，输出最终故事。
  3. 加两个并行检查 Agent：事实核查、风格检查，分别写不同 outputKey。
  4. 用一个汇总 Agent 读取两个检查结果，决定是否重写。
  5. 进阶：改成 loopBuilder，最多迭代 3 次，满足字数条件就退出。
