06 · Tool Calling：让模型调用你的 Java 方法

前面模型只能「说」。这一章让它「做」：查订单、算价格、调内部 API。 你会先跑通一个订单查询工具，再逐步理解工具描述、用户身份、失败回传与执行顺序。 最后做一个「订单 + 退款」双工具助手。

学完这一章，你能做什么

  • 用 @Tool 把 Java 方法暴露给模型
  • 用 @P 写清参数，减少模型瞎填
  • 用 InvocationContext 把用户身份带进工具
  • 理解工具失败、执行顺序与工具循环

先理解：模型不能直接执行 Java

模型只会输出文本。所谓「工具调用」，是它输出一段结构化请求： 

我要调用 queryOrder，参数是 {"orderNo":"SO-20261106-001"}

框架解析这段请求、找到你的 Java 方法、执行、把结果再发回模型。 模型始终没有执行权限；真正的鉴权、事务、数据库访问都在 Java 侧。

这也是安全边界：用户 id、租户 id 必须来自服务端，不能让模型填。

第一步：让模型查一次订单

class OrderTools {
    @Tool("按订单号查询订单状态，只读")
    String queryOrder(@P("订单号，例如 SO-20261106-001") String orderNo) {
        return orderService.statusOf(orderNo);
    }
}

interface SupportAssistant {
    String ask(String question);
}

SupportAssistant assistant = AiServices.builder(SupportAssistant.class)
        .chatModel(model)
        .tools(new OrderTools())
        .build();

System.out.println(assistant.ask("帮我查一下 SO-20261106-001 到哪了"));

运行后，框架内部会发生四步：

  1. 第一次模型调用
    模型返回一个 tool_calls，要求执行 queryOrder。
  2. 执行工具
    框架把参数 JSON 转成 Java 参数，调用你的方法。
  3. 回填结果
    把返回值作为工具结果消息追加到上下文。
  4. 第二次模型调用
    模型基于工具结果生成最终回答。

第二步：把工具描述写清楚

模型靠描述决定「调不调、调哪个、参数怎么填」。描述写得含糊，工具就会「看起来存在但永远不被调用」。

写法模型会怎么理解
@Tool("查询订单")知道能查，但不知道参数格式
@Tool("按订单号查询订单状态，只读，返回 PAID/SHIPPED/DELIVERED")知道什么时候用、输入输出是什么
@P("订单号，例如 SO-20261106-001")知道参数格式与示例

返回值会被序列化：返回对象是 JSON，返回 void 时发送 "Success"。 不要把敏感字段（密码、完整手机号）直接作为返回值。

P.java:44

第三步：把用户身份带进工具

工具参数里绝对不能让模型填 userId。正确做法是从 InvocationContext 读取服务端传入的会话信息： 

@Tool("查询当前用户的订单")
String myOrder(String orderNo, InvocationContext ctx) {
    String userId = String.valueOf(ctx.chatMemoryId());
    return orderService.find(userId, orderNo);
}

chatMemoryId() 来自 AI Service 的 @MemoryId 参数。 如果你需要更多自定义信息（租户、角色），可以在调用时传 InvocationParameters，再从工具里读。

第四步：工具失败时怎么回

工具失败有两种处理方式：

  • 抛异常：默认同步模式下，框架会把异常消息回给模型，让模型换方案。
  • 返回错误文案：自己 catch，把「失败原因 + 建议」作为正常返回值。
@Tool("转账")
String transfer(String from, String to, long cents) {
    bank.transfer(from, to, cents);   // 失败时抛业务异常
    return "转账成功";
}
不要返回 ToolExecutionResult 来控制错误

ToolExecutionResult 是框架内部的执行结果包装。工具方法直接返回它时， 框架会把它当普通对象序列化成 JSON，不会读取其中的 isError。 要自定义错误文案，用 toolExecutionErrorHandler；要完全控制执行，用自定义 ToolExecutor。

ToolService.java:104

第五步：多个工具与执行顺序

模型可能一轮返回多个工具调用。同步与 TokenStream 模式默认顺序执行； 异步 / 响应式模式默认并发。需要并发时显式开启： 

SupportAssistant assistant = AiServices.builder(SupportAssistant.class)
        .chatModel(model)
        .tools(new OrderTools(), new RefundTools())
        .executeToolsConcurrently()
        .build();

有顺序依赖的工具（先锁库存、再扣款）不要开并发，拆成多个工具或让模型分轮调用。 不要假设多个工具一定按数组顺序执行。

AiServices.java:663

第六步：工具循环到底发生了什么

一次工具调用不是「模型 → 工具 → 结束」，而是「模型 → 工具 → 模型」的循环。 如果模型一直要求调用工具，循环会持续。可以设置上限： 

SupportAssistant assistant = AiServices.builder(SupportAssistant.class)
        .chatModel(model)
        .tools(new OrderTools())
        .maxToolCallingRoundTrips(5)
        .build();

调试时打开请求/响应日志，确认模型到底发了哪个工具、参数是什么、结果回了什么。 很多「模型不调用工具」其实是描述或参数 schema 的问题，不是模型能力问题。

常见错误与排查

1. 模型不调用工具
你会看到
回答正常，但工具没执行。
因为
描述太模糊、参数没描述、模型不支持 function calling。
改成
把 @Tool 描述写成「什么时候用、输入是什么、返回什么」；先用明确指令测试。
2. 参数类型不匹配
你会看到
工具执行前就报参数转换错误。
因为
模型给了字符串，方法要 int/long；或日期格式不一致。
改成
用简单类型，或在描述里写清格式；复杂参数让模型传 JSON 字符串后自己解析。
3. 工具结果太长撑爆上下文
你会看到
后续回答变慢、变差，甚至报上下文超限。
因为
工具返回了整页 HTML 或大对象。
改成
工具只返回摘要字段；大结果落盘或分页。
4. 工具循环停不下来
你会看到
模型反复调用同一个工具。
因为
工具结果没有解决模型的问题，或描述让模型误以为必须继续。
改成
设置 maxToolCallingRoundTrips；在工具结果里明确「已完成/无法完成」。

动手练习：订单 + 退款助手

把客服助手升级成双工具：

  1. queryOrder(orderNo)：只读，返回状态与预计到达时间。
  2. refund(orderNo, reason)：写操作，要求用户身份来自 @MemoryId。
  3. 给两个工具都写清 @Tool 与 @P 描述。
  4. 让模型先查订单，再决定是否退款；观察工具调用顺序。
  5. 进阶：把退款工具改成失败时抛异常，看模型如何向用户解释。
判断自己学会了没有

如果你能画出「模型 → 工具 → 模型」的循环，并解释用户身份为什么不能由模型填， 这一章就过关了。
