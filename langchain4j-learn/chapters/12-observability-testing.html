12 · 可观测性、测试与评测：知道它为什么慢、为什么变差

AI 应用出问题时，最难回答的三个问题是：这次到底发了什么？为什么这么慢/贵？改了 prompt 之后质量有没有下降？ 这一章按这三问，逐层加监听器、指标、trace、请求断言、Judge 与回归集。

学完这一章，你能做什么

  • 用 ChatModelListener 记录每次模型调用
  • 接 Micrometer 看延迟与 token 用量
  • 用 Observation 把一次调用串成 trace
  • 给提示词和工具面写稳定的请求断言
  • 用 Judge 与回归集判断质量变化

先理解：出问题时你最想知道什么

问题需要的工具本章对应
这次请求发了什么、回了什么？监听器 / 日志第一步
为什么慢、为什么贵？指标 / trace第二、三步
提示词和工具面有没有被改坏？请求断言第四步
回答质量有没有下降？Judge + 回归集第五、六步

不要一上来全量记录 prompt。先想清楚要回答哪个问题，再选最小工具。

第一步：记录每次模型调用

ChatModelListener 有请求、响应、错误三个回调。它拿得到请求、响应与异常， 但拿不到业务上下文，除非你把上下文放进属性。 

ChatModelListener listener = new ChatModelListener() {
    @Override
    public void onRequest(ChatModelRequestContext ctx) {
        log.info("model={} messages={}",
                ctx.chatRequest().parameters().modelName(),
                ctx.chatRequest().messages().size());
    }

    @Override
    public void onResponse(ChatModelResponseContext ctx) {
        log.info("usage={}", ctx.chatResponse().tokenUsage());
    }

    @Override
    public void onError(ChatModelErrorContext ctx) {
        log.warn("model call failed", ctx.error());
    }
};

ChatModel model = OpenAiChatModel.builder()
        .baseUrl("https://api.deepseek.com/v1")
        .apiKey(System.getenv("DEEPSEEK_API_KEY"))
        .modelName("deepseek-chat")
        .listeners(listener)
        .build();

上线时不要无条件打印完整 prompt / completion：里面有用户隐私、密钥、内部数据。 至少做采样或脱敏。

第二步：看延迟与 token 成本

MicrometerMetricsChatModelListener 把调用时长与 token 用量写进 MeterRegistry，指标名遵循 OpenTelemetry GenAI 约定：

指标回答什么
gen_ai.client.operation.duration模型调用耗时分布
gen_ai.client.token.usage输入/输出 token 用量
 
MeterRegistry registry = new SimpleMeterRegistry();
ChatModel model = OpenAiChatModel.builder()
        .baseUrl("https://api.deepseek.com/v1")
        .apiKey(System.getenv("DEEPSEEK_API_KEY"))
        .modelName("deepseek-chat")
        .listeners(new MicrometerMetricsChatModelListener(registry))
        .build();

生产环境通常会把这些指标接到 Prometheus / Grafana，按模型、租户、接口维度看 P95 与成本。

第三步：把一次调用串成 trace

指标告诉你「慢了」，trace 告诉你「慢在哪一段」。 ObservationChatModelListener 用 Micrometer Observation 创建 span， 需要 ObservationRegistry 与 MeterRegistry： 

ChatModelListener listener = new ObservationChatModelListener(
        observationRegistry, meterRegistry);

ChatModel model = OpenAiChatModel.builder()
        .baseUrl("https://api.deepseek.com/v1")
        .apiKey(System.getenv("DEEPSEEK_API_KEY"))
        .modelName("deepseek-chat")
        .listeners(listener)
        .build();

把检索、工具、模型调用都放在同一个 trace 里，才能看出是检索慢、工具慢，还是模型慢。

第四步：给提示词和工具面写断言

不要只断言最终字符串，模型输出会波动。更稳的是断言「请求长什么样」： 系统提示有没有带上、用户模板有没有渲染、工具有没有注册。 

class CapturingModel implements ChatModel {
    ChatRequest last;
    @Override public ChatResponse doChat(ChatRequest request) {
        this.last = request;
        return ChatResponse.builder().aiMessage(AiMessage.from("ok")).build();
    }
}

CapturingModel model = new CapturingModel();
SupportAssistant assistant = AiServices.create(SupportAssistant.class, model);
assistant.chat("你好");

LangChain4jAssertions.assertThat(model.last)
        .hasSystemMessageContaining("简洁")
        .hasUserMessageContaining("你好");

这样即使模型换成别的 provider，只要请求结构没变，测试就仍然有效。

LangChain4jAssertions.java:34 ChatRequestAssert.java:60

第五步：用 Judge 判断回答质量

「回答是否包含退款期限」这种标准，很难用字符串断言。用 Judge 把自然语言标准交给一个评审模型： 

Judge judge = Judge.from(judgeModel);

judge.assertThat(answer)
        .given("退款需要几天？")
        .satisfies("回答提到 7 个工作日", "没有编造额外日期");

judge 建议用不同模型家族、固定版本，并尽量设置 temperature 0。 自评会偏乐观；judge 也会犯错，保留人工抽检。

RAG 场景可以用 basedOnContents(result.sources()) 把召回内容交给 judge， 检查回答是否只基于这些来源。

第六步：把评测放进 CI

准备一份 JSONL：问题、期望要点、可选来源。每次改动跑一遍，记录通过率与 token 成本。 检索侧看 recall@k / MRR，生成侧看 Judge 通过率；两者不要混成一个分数。 

{"question":"退款需要几天？","mustMention":["7 个工作日"],"sources":["refund.md"]}
{"question":"可以退运费吗？","mustMention":["满 99 包邮"],"sources":["shipping.md"]}
  • 固定 judge 模型与版本，避免「judge 升级」导致基线漂移。
  • 给失败样本保留请求、响应与召回内容，方便回放。
  • CI 里只跑小回归集；大集放夜间任务，控制成本。

第七步：采样、脱敏与成本

  • 默认不要全量记录 prompt / completion；按采样率或错误触发。
  • 日志脱敏：手机号、身份证、密钥不能进日志与 trace。
  • token 指标按模型与租户打标签，但别把用户 id 放进高基数标签。
  • judge 调用本身也花钱，评测预算要和线上预算分开。

常见错误与排查

1. 监听器没触发
你会看到
日志里没有请求记录。
因为
只创建了 listener，没有通过 .listeners(...) 挂到模型上。
改成
确认模型 builder 上挂了 listener；流式模型也要单独挂。
2. tokenUsage 为 null
你会看到
指标或日志里用量为空。
因为
不是所有 provider / 模型都返回用量。
改成
判空后再记录；没有用量时用估算值并标注来源。
3. Judge 结果不稳定
你会看到
同一批样本每次通过率差很多。
因为
judge 模型随机性、criterion 太模糊、模型版本漂移。
改成
temperature 0、固定版本、一条 criterion 只判断一件事。
4. 观测本身拖慢应用
你会看到
加了监听后延迟上升。
因为
同步写日志、全量序列化大对象。
改成
异步日志、采样、只记录摘要字段。

动手练习：给客服助手加观测与回归

  1. 给模型挂一个 listener，记录模型名、消息数与 token 用量。
  2. 接 Micrometer，观察一次调用的 duration 与 token 指标。
  3. 用捕获请求的假模型，断言系统提示包含「电商客服」。
  4. 准备 10 条回归样本，用 Judge 判断回答是否提到关键事实。
  5. 进阶：给 10 条样本记录基线通过率，改一次 prompt 后对比。
