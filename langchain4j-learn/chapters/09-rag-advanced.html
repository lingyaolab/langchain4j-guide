09 · RAG 进阶：当基础 RAG 不够用

上一章的 RAG 只会「拿原问题去查一个库」。真实业务里很快会遇到三种情况： 用户问「那退款呢？」这种追问、公司有多个知识库、查回来的内容排序不对。 这一章按这三个问题，逐个加上查询改写、路由、动态参数、聚合与重排。

学完这一章，你能做什么

  • 把多轮追问改写成可检索的完整问题
  • 让不同问题路由到不同知识库
  • 按问题动态调整 topK 与阈值
  • 合并多路结果，并用重排模型提升排序
  • 用回归集判断改动有没有变好

先理解：基础 RAG 什么时候不够用

现象基础 RAG 为什么不行本章对应
「那退款呢？」召回为空问题本身缺少主语，向量检索抓不到关键词查询改写
售前问题命中了内部运维文档只有一个库，所有问题都往同一个库查路由
简单问题召回太多、复杂问题召回太少topK / 阈值固定动态检索参数
正确片段排在第 8 位只看向量相似度，没有重排聚合与重排

注意：不要一上来全开。链路越长，延迟和成本越高。先定位问题，再选一段加策略。

第一步：把追问改写成完整问题

「那退款呢？」在上一轮聊运费时，真实意思是「退款政策和流程是什么」。 CompressingQueryTransformer 会结合历史，把它压成一个独立问题： 

QueryTransformer compress = new CompressingQueryTransformer(model);

如果一个问题可以从多个角度查，用 ExpandingQueryTransformer 生成多个变体： 

QueryTransformer expand = new ExpandingQueryTransformer(model, 3);

默认生成 3 个变体。变体越多，召回覆盖越广，但检索次数和延迟也越高。

CompressingQueryTransformer.java:41 ExpandingQueryTransformer.java:38

第二步：让问题去正确的知识库

假设你有两个库：docs（产品文档）和 tickets（工单记录）。 DefaultQueryRouter 会把每个查询发给所有 retriever： 

ContentRetriever docs = EmbeddingStoreContentRetriever.builder()
        .embeddingStore(docsStore).embeddingModel(embeddingModel).maxResults(4).build();

ContentRetriever tickets = EmbeddingStoreContentRetriever.builder()
        .embeddingStore(ticketStore).embeddingModel(embeddingModel).maxResults(4).build();

QueryRouter router = new DefaultQueryRouter(docs, tickets);

如果库很多、问题只该去其中一个，用 LanguageModelQueryRouter， 让模型根据 retriever 描述选择一个或多个。代价是多一次模型调用。

DefaultQueryRouter.java:28 LanguageModelQueryRouter.java:48

第三步：按问题动态调整 topK 与阈值

「对比 A 和 B」需要更多片段，「退货几天」只需要一两条。不要让所有问题共用一套参数： 

ContentRetriever retriever = EmbeddingStoreContentRetriever.builder()
        .embeddingStore(store)
        .embeddingModel(embeddingModel)
        .dynamicMaxResults(q -> q.text().contains("对比") ? 8 : 4)
        .dynamicMinScore(q -> 0.6)
        .build();

默认 maxResults 是 3、minScore 是 0.0。 minScore 是向量库查询条件，不是「先取满再过滤」； 阈值太高会直接减少召回条数。

EmbeddingStoreContentRetriever.java:72 EmbeddingStoreContentRetriever.java:73

第四步：合并多路结果并重排

多路召回会重复。DefaultContentAggregator 用 RRF（按排名融合）去重合并： 

ContentAggregator rrf = new DefaultContentAggregator();

如果向量相似度排序不准，可以再接一层 ScoringModel 重排： 

ContentAggregator rerank = ReRankingContentAggregator.builder()
        .scoringModel(scoringModel)
        .maxResults(6)
        .build();
多查询 + 重排要配 querySelector

重排默认只支持单查询。前面用了 ExpandingQueryTransformer 时， 必须再传 querySelector(...) 指定用哪个查询打分，否则聚合阶段会抛参数异常。

DefaultContentAggregator.java:55 ReRankingContentAggregator.java:51

第五步：把四段串成一条链路

RetrievalAugmentor augmentor = DefaultRetrievalAugmentor.builder()
        .queryTransformer(new CompressingQueryTransformer(model))
        .queryRouter(new DefaultQueryRouter(docs, tickets))
        .contentAggregator(ReRankingContentAggregator.builder()
                .scoringModel(scoringModel)
                .maxResults(6)
                .build())
        .build();

SupportAssistant assistant = AiServices.builder(SupportAssistant.class)
        .chatModel(model)
        .retrievalAugmentor(augmentor)
        .build();

ContentRetriever 必须由你提供；DefaultQueryRouter 只在调用 builder().contentRetriever(...) 时自动创建。 直接传 queryRouter 时，路由和检索都由你负责。

第六步：用回归集判断有没有变好

「感觉回答更好了」不算数。准备 30–50 条样本，分成三类：

  • 答案在文档里：看 recall@k、MRR。
  • 答案不在文档里：看模型是否明确说「资料中没有」。
  • 需要多跳检索：看是否正确合并多个片段。

每次只改一个变量（改写、topK、阈值、重排），跑同一套样本，记录召回与回答质量。 否则你无法判断是哪一步带来的变化。

常见错误与排查

1. 改写后反而召回为空
你会看到
原来能查到的片段，改写后查不到。
因为
改写模型把关键实体改丢了，或改成了更泛的说法。
改成
保留原问题一起查，或换更小的改写模型；对比改写前后召回。
2. 多知识库互相污染
你会看到
售前问题召回内部运维文档。
因为
DefaultQueryRouter 把查询发给了所有库。
改成
用 LanguageModelQueryRouter，或按业务先过滤 retriever。
3. 重排报错
你会看到
多查询场景下重排抛参数异常。
因为
没有提供 querySelector。
改成
显式指定用哪个查询打分，或只保留单查询链路。
4. 链路太慢
你会看到
首字延迟从 1 秒涨到 5 秒。
因为
改写 + 多查询 + 重排叠加了多次模型/检索调用。
改成
按场景裁剪；先定位是召回问题还是排序问题。

动手练习：多知识库客服

  1. 准备两个库：产品文档、退款政策。
  2. 用 DefaultQueryRouter 先跑通多路召回。
  3. 加 CompressingQueryTransformer，对比「那退款呢？」改写前后的召回。
  4. 把 maxResults 改成动态参数，记录延迟变化。
  5. 进阶：接一个 ScoringModel 重排，比较正确片段的名次。
判断自己学会了没有

如果你能针对「召回为空 / 串库 / 排序不对」分别选出对应策略， 并说清代价，这一章就过关了。
