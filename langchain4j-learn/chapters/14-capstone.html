14 · 综合案例：搭一个知识库客服服务

前面每一章只解决一个问题。这一章把它们串起来：一个客服服务，能查知识库、查订单、 记住用户、流式返回。我们不会一次写完所有代码，而是按「建工程 → 入库 → 检索 → 工具 → 记忆 → 流式 → 接口 → 测试 → 部署」九步搭起来。

学完这一章，你能做什么

  • 把 RAG、工具、记忆、流式接进同一个 AI Service
  • 写出可运行的文档入库与检索链路
  • 把 TokenStream 转成 SSE
  • 给服务补测试、超时、限流与部署配置

先理解：一条请求怎么走

HTTP 请求
  → 鉴权 / 限流
  → SupportAssistant（AI Service）
  → 读取记忆
  → 检索知识库
  → 模型 + 工具循环
  → TokenStream
  → SSE 返回
层职责
接口层鉴权、限流、请求校验、SSE 生命周期
AI Service提示词、记忆、RAG、工具编排
知识库入库、切分、向量化、检索
工具订单、物流等业务查询

第二步：把文档入库

EmbeddingModel embeddingModel = new AllMiniLmL6V2EmbeddingModel();
EmbeddingStore<TextSegment> store = new InMemoryEmbeddingStore<>();

Document document = FileSystemDocumentLoader.loadDocument(
        Path.of("docs/refund.md"), new TextDocumentParser());

EmbeddingStoreIngestor ingestor = EmbeddingStoreIngestor.builder()
        .documentSplitter(DocumentSplitters.recursive(500, 50))
        .embeddingModel(embeddingModel)
        .embeddingStore(store)
        .build();

ingestor.ingest(document);

入库是离线任务。文档变更后重建对应片段，不要在每次用户提问时重新解析整份文档。

DocumentSplitters.java:45 EmbeddingStoreIngestor.java:54

第三步：接上检索

ContentRetriever retriever = EmbeddingStoreContentRetriever.builder()
        .embeddingStore(store)
        .embeddingModel(embeddingModel)
        .maxResults(4)
        .minScore(0.6)
        .build();

先用低阈值观察召回，再逐步调高；空召回时宁可回答「资料中没有」，不要让模型自由发挥。

第四步：接上订单工具

class OrderTools {
    @Tool("按订单号查询订单状态，只读")
    OrderView queryOrder(@P("订单号") String orderNo, InvocationContext ctx) {
        String userId = String.valueOf(ctx.chatMemoryId());
        return orderService.find(userId, orderNo);
    }
}

用户 id 来自 @MemoryId，工具通过 chatMemoryId() 读取。 绝不能让模型填 userId，否则可以查别人的订单。

Tool.java:26 InvocationContext.java:24

第五步：接上多用户记忆

interface SupportAssistant {
    @SystemMessage("只根据提供的上下文回答；不知道就说资料中没有")
    TokenStream chat(@MemoryId String userId, @UserMessage String question);
}

@MemoryId 让每个用户有独立上下文；窗口大小由 provider 控制。

MessageWindowChatMemory.java:269

第六步：把回答改成 SSE

SupportAssistant assistant = AiServices.builder(SupportAssistant.class)
        .streamingChatModel(streamingModel)
        .chatMemoryProvider(id -> MessageWindowChatMemory.withMaxMessages(20))
        .contentRetriever(retriever)
        .tools(new OrderTools())
        .build();

TokenStream stream = assistant.chat(userId, question);
stream.onPartialResponse(token -> emitter.send(SseEmitter.event().data(token)))
      .onCompleteResponse(r -> emitter.complete())
      .onError(emitter::completeWithError)
      .start();

接口只返回 TokenStream，所以只配 streamingChatModel， 不同时配 chatModel。上面的 SseEmitter 是 Spring MVC 示例。

AiServices.java:258 TokenStream.java:43 TokenStream.java:244

第七步：加鉴权、限流与错误处理

  • 鉴权后把 userId 放进会话或 InvocationParameters。
  • 按用户/租户限流；流式请求设置最长生命周期。
  • 模型错误返回统一错误码；不要把内部堆栈返回给前端。
  • SSE 断开时，用带 context 的回调拿到 StreamingHandle 并取消。

第八步：测试与回归

  • 用捕获请求的假模型断言系统提示与工具面。
  • 用 Judge 检查回答是否基于召回内容。
  • 准备 30–50 条回归样本，覆盖「有答案 / 无答案 / 需要工具」。
  • 把超时、降级与限流也做成可测试的配置。

第九步：部署与配置

app:
  model:
    base-url: https://api.deepseek.com/v1
    name: deepseek-chat
  rag:
    top-k: 4
    min-score: 0.6
  limits:
    max-output-tokens: 800
    request-timeout: 90s

密钥用环境变量注入；pgvector 连接串、模型地址、限流参数都走配置中心。

常见错误与排查

1. 把入库放在请求里
你会看到
第一次回答非常慢。
因为
解析 PDF、调 embedding 都在请求路径里。
改成
入库放离线任务或后台队列。
2. 工具与 RAG 抢上下文
你会看到
回答变差，甚至上下文超限。
因为
topK 太大 + 工具结果太长。
改成
分别设上限，监控 token 用量。
3. 流式错误发生在响应头之后
你会看到
已经返回 200，前端却收不到完整内容。
因为
响应头发出后不能再改状态码。
改成
通过 SSE 错误事件收尾，并记录 trace。
4. 同时配同步与流式模型
你会看到
配置异常。
因为
AI Service 要求二选一。
改成
返回 TokenStream 的接口只配 streamingChatModel。
