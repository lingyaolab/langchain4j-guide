14 · 综合案例：知识库 + 工具 + 流式

把模型、RAG、工具、记忆与流式串成一个可运行服务，含入库、SSE、测试与部署。

读完你能做到

  • 把 RAG、工具、记忆与流式接进同一个 AI Service
  • 写出可运行的文档入库与检索链路
  • 把 TokenStream 转成 SSE
  • 给这个服务补测试、超时、限流与部署配置

架构：一条请求怎么走

一条请求依次经过：HTTP 层鉴权 / 限流 → SupportAssistant（AI Service）→ 记忆注入 → 查询改写 / 检索 → 模型 + 工具循环 → TokenStream → SSE 返回。

层职责
接口层鉴权、限流、请求校验、SSE 生命周期
AI Service提示词、记忆、RAG、工具编排
知识库入库、切分、向量化、检索
工具订单、物流等业务查询

检索：ContentRetriever 与阈值

ContentRetriever retriever = EmbeddingStoreContentRetriever.builder()
        .embeddingStore(store)
        .embeddingModel(embeddingModel)
        .maxResults(4)
        .minScore(0.6)
        .build();

先用较低阈值观察召回，再逐步调高；空召回时宁可回答「资料中没有」， 不要让模型自由发挥。

工具：订单查询与用户上下文

class OrderTools {
    @Tool("按订单号查询订单状态")
    OrderView queryOrder(@P("订单号") String orderNo, InvocationContext ctx) {
        String userId = String.valueOf(ctx.chatMemoryId());
        return orderService.find(userId, orderNo);
    }
}

用户 id 必须来自服务端会话或 @MemoryId（工具里通过 InvocationContext.chatMemoryId() 读取），不能由模型填。 否则模型可以伪造参数查别人的订单。

流式：TokenStream 到 SSE

SupportAssistant assistant = AiServices.builder(SupportAssistant.class)
        .streamingChatModel(streamingModel)
        .chatMemoryProvider(id -> MessageWindowChatMemory.withMaxMessages(20))
        .contentRetriever(retriever)
        .tools(new OrderTools())
        .build();

TokenStream stream = assistant.chat(userId, question);
stream.onPartialResponse(token -> emitter.send(SseEmitter.event().data(token)))
      .onCompleteResponse(r -> emitter.complete())
      .onError(emitter::completeWithError)
      .start();

接口层：鉴权、限流与错误

  • 鉴权后把 userId 放进会话或 InvocationParameters。
  • 按用户/租户限流；流式请求设置最长生命周期。
  • 模型错误返回统一错误码；不要把内部堆栈返回给前端。
  • SSE 断开时，用 onPartialResponseWithContext 拿到 StreamingHandle 并调用 cancel()；普通 onPartialResponse 不提供取消句柄。

测试：断言、Judge 与回归

  • 用捕获请求的假模型断言系统提示与工具面。
  • 用 Judge 检查回答是否基于召回内容。
  • 准备 30–50 条回归样本，覆盖「有答案 / 无答案 / 需要工具」。
  • 把超时、降级与限流也做成可测试的配置。

陷阱与窍门

把入库放在请求里

解析 PDF / 调 embedding 很慢；入库必须是离线任务或后台队列。

工具与 RAG 抢同一个上下文窗口

topK 太大 + 工具结果太长会挤爆上下文；分别设上限并监控 token。

流式错误发生在响应头之后

已经发 200 就只能通过 SSE 错误事件收尾，不能改状态码。
