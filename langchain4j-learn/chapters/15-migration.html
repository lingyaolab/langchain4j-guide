从 Spring AI 映射过来

两者都提供「模型 + 提示词 + 工具 + 记忆 + RAG」，但抽象不同：Spring AI 以 ChatClient 与 Advisor 链为中心；LangChain4j 以 ChatModel、 AI Service 接口与显式 RAG 组件为中心。

QuestionAnswerAdvisorContentRetriever / RetrievalAugmentor
@Tool@Tool + AI Service 工具循环

概念对照：哪些能一一对应

  • 能对应：模型接口、消息类型、工具注解、记忆窗口、向量库、Embedding。
  • 不能一一对应：Advisor 链在 LangChain4j 里没有同名机制，记忆 / RAG / 工具各自是独立组件。
  • 默认行为不同：RAG 的查询改写、阈值、topK 默认值不同，迁移后必须重新评测。

迁移步骤：从 0.x 到 1.x

  1. 先换依赖
    收口到 langchain4j-bom，移除手写版本。
  2. 再换接口
    0.x 的 ChatLanguageModel 统一为 ChatModel。
  3. 重写工具上下文
    用 InvocationContext / InvocationParameters，不要沿用旧的 ToolContext。
  4. 重建 RAG
    按 ContentRetriever + RetrievalAugmentor 重新接，不要只改包名。
  5. 补评测
    用同一回归集对比迁移前后的召回与回答质量。

选型与迁移检查清单

检查项为什么
是否需要声明式接口AI Service 能显著减少模板代码
是否需要 Advisor 式横切LangChain4j 更倾向显式组件组合
RAG 默认值是否一致topK / 阈值 / 改写策略不同
工具与 MCP 治理LangChain4j 用 ToolProvider / 白名单
观测与评测监听器、指标、Judge 要提前接

陷阱与窍门

按类名一一替换

Advisor、ChatClient、RAG 的抽象不同；按行为重写，别只做 import 替换。

迁移后不做回归

默认阈值、切分与提示词都会影响结果；没有基线就无法判断是否变差。
