15 · 迁移与选型：Spring AI 与 LangChain4j 怎么选

学到这里，你可能会问：我已经在用 Spring AI，要不要换 LangChain4j？ 这一章不做「谁更好」的结论，而是给出边界、概念对照、API 对照和迁移步骤， 让你按项目情况做决定。

先理解：Spring AI 与 LangChain4j 的边界

维度Spring AILangChain4j
生态Spring Boot / Spring 生态框架无关，纯 Java 库
核心抽象ChatClient + Advisor 链ChatModel + AI Service + 显式组件
RAGAdvisor 形式接入ContentRetriever / RetrievalAugmentor
适合已有 Spring 服务、想快速接入想控制调用链、跨框架、细粒度组件组合

两者不是互斥的：Spring 项目可以用 LangChain4j，非 Spring 项目也能单独用 Spring AI 的模型模块。 选型的核心是「你的项目更依赖哪套抽象」。

概念对照：哪些能一一对应

能对应的部分迁移成本低；不能一一对应的是 Advisor 链。LangChain4j 更倾向把记忆、RAG、工具拆成独立组件， 不要指望按类名替换就能等价迁移。

版本与依赖：1.23.0 怎么选

BOM 版本是 1.23.0；稳定模块跟 BOM，实验模块是 1.23.0-beta33。 迁移时只写 BOM 版本，不要手写各模块版本。

迁移步骤：从 Spring AI 或 0.x 过来

  1. 先换依赖
    收口到 langchain4j-bom，移除手写版本。
  2. 再换接口
    0.x 的 ChatLanguageModel 统一为 ChatModel。
  3. 重写工具上下文
    用 InvocationContext / InvocationParameters，不要沿用旧的 ToolContext。
  4. 重建 RAG
    按 ContentRetriever + RetrievalAugmentor 重新接，不要只改包名。
  5. 补评测
    用同一回归集对比迁移前后的召回与回答质量。

选型与迁移检查清单

检查项为什么
是否深度依赖 Spring 生态依赖越深，留在 Spring AI 越省事
是否需要细粒度控制调用链LangChain4j 的组件拆分更显式
RAG 默认值是否一致topK / 阈值 / 改写策略不同
工具与 MCP 治理LangChain4j 用 ToolProvider / 白名单
观测与评测监听器、指标、Judge 要提前接

常见错误与排查

1. 按类名一一替换
你会看到
编译过了，行为却不一样。
因为
Advisor、ChatClient、RAG 的抽象不同。
改成
按行为重写，别只做 import 替换。
2. 迁移后不做回归
你会看到
回答突然变差，但不知道哪儿变了。
因为
默认阈值、切分与提示词都会影响结果。
改成
先准备基线，再逐项对比。
3. 把 beta 版本写进稳定模块
你会看到
依赖解析失败或运行时链接错误。
因为
稳定模块与实验模块版本不同。
改成
只写 BOM 版本，模块不写版本。
4. 忽略 JDK 要求
你会看到
编译报 release 17 不支持。
因为
项目还在 JDK 8/11。
改成
升级到 JDK 17；LangChain4j 1.23.0 的编译目标就是 17。
