07 · Memory：让助手记住上一轮

上一章的助手每次对话都从零开始。这一章解决「记得住」： 先用手动列表理解原理，再换成窗口记忆，最后按用户隔离，并把记忆存到 Redis / JDBC。

学完这一章，你能做什么

  • 理解模型为什么不记得上一轮
  • 用 MessageWindowChatMemory 控制上下文长度
  • 把记忆接进 AI Service，做多轮对话
  • 用 @MemoryId 按用户隔离
  • 实现一个自定义 ChatMemoryStore

先理解：模型本身不记得上一轮

模型接口是无状态的。你问「我叫什么」，它不知道，是因为这次请求里根本没有上一轮的消息。 多轮对话的本质是：每次把历史消息一起发过去。 

List<ChatMessage> history = new ArrayList<>();
history.add(UserMessage.from("我叫小明"));
history.add(AiMessage.from("你好，小明"));
history.add(UserMessage.from("我叫什么？"));

ChatResponse response = model.chat(ChatRequest.builder()
        .messages(history)
        .build());

手动维护能跑，但很快会遇到：窗口无限增长、忘记写回 AI 回答、多用户串数据。 ChatMemory 就是把这套逻辑收起来。

第一步：用窗口记忆做多轮对话

ChatMemory memory = MessageWindowChatMemory.withMaxMessages(10);

memory.add(UserMessage.from("我叫小明"));
memory.add(AiMessage.from("你好，小明"));
memory.add(UserMessage.from("我叫什么？"));

System.out.println(memory.messages());

withMaxMessages(10) 表示最多保留 10 条消息。注意：窗口大小必须显式设置， builder().build() 不设 maxMessages 会失败。

第二步：看懂窗口淘汰规则

窗口满了会淘汰旧消息，但不是简单删第一条：

  • 如果第一条是 SystemMessage，会跳过它，从第二条开始淘汰，尽量保留系统提示。
  • 如果淘汰的是一条带工具调用的 AiMessage，紧跟其后的 ToolExecutionResultMessage 也会一起删掉，避免出现「孤儿工具结果」。
  • 消息总数仍然受 maxMessages 限制，不会无限增长。

这解释了为什么窗口太小时，模型可能「忘了前面说过什么」；不是记忆坏了，是旧消息被淘汰了。

第三步：把记忆接进 AI Service

不需要手动 add。AI Service 会在调用前读取记忆、调用后写回： 

ChatMemory memory = MessageWindowChatMemory.withMaxMessages(10);

SupportAssistant assistant = AiServices.builder(SupportAssistant.class)
        .chatModel(model)
        .chatMemory(memory)
        .build();

System.out.println(assistant.chat("我叫小明"));
System.out.println(assistant.chat("我叫什么？"));

第二轮能答出「小明」，说明记忆生效。内部顺序是： before 读取历史 → 调模型 → after 追加 user / AI 消息。

第四步：按用户隔离记忆

一个 ChatMemory 被所有用户共用，就会串数据。多用户用 chatMemoryProvider + @MemoryId： 

interface SupportAssistant {
    String chat(@MemoryId String userId, @UserMessage String message);
}

SupportAssistant assistant = AiServices.builder(SupportAssistant.class)
        .chatModel(model)
        .chatMemoryProvider(id -> MessageWindowChatMemory.withMaxMessages(10))
        .build();

assistant.chat("user-A", "我叫小明");
assistant.chat("user-B", "我叫什么？");   // 不应该知道小明

@MemoryId 的值会传给 provider。生产环境建议用 tenantId + ":" + userId，避免不同租户撞键。

第五步：把记忆存到 Redis / JDBC

默认的窗口记忆把消息放在内存里，进程重启就丢。要持久化，实现 ChatMemoryStore 的三个方法： 

class RedisChatMemoryStore implements ChatMemoryStore {
    public List<ChatMessage> getMessages(Object memoryId) {
        String json = redis.get(String.valueOf(memoryId));
        return json == null ? List.of() : ChatMessageDeserializer.messagesFromJson(json);
    }

    public void updateMessages(Object memoryId, List<ChatMessage> messages) {
        redis.set(String.valueOf(memoryId), ChatMessageSerializer.messagesToJson(messages));
    }

    public void deleteMessages(Object memoryId) {
        redis.del(String.valueOf(memoryId));
    }
}

然后把 store 交给窗口记忆： 

ChatMemory memory = MessageWindowChatMemory.builder()
        .id("user-A")
        .maxMessages(10)
        .chatMemoryStore(new RedisChatMemoryStore())
        .build();

常见错误与排查

1. 多轮对话「失忆」
你会看到
第二轮不知道第一轮说过什么。
因为
没有配 chatMemory，或每次新建了一个空记忆。
改成
把同一个 ChatMemory 传给 builder；多用户用 provider。
2. A 用户看到 B 用户历史
你会看到
不同用户共享上下文。
因为
所有请求共用一个 ChatMemory。
改成
用 @MemoryId + chatMemoryProvider。
3. 窗口太小
你会看到
刚说过的话很快忘掉。
因为
maxMessages 设得太小，旧消息被淘汰。
改成
按场景调到 20–50；长对话靠摘要，不要无限加大窗口。
4. 重启后记忆全丢
你会看到
服务重启后用户历史消失。
因为
用了默认内存 store。
改成
实现 ChatMemoryStore 接 Redis / JDBC，并保证消息 JSON 可反序列化。

动手练习：多用户客服记忆

把上一章客服助手升级成有记忆的版本：

  1. 用 @MemoryId 按用户隔离，窗口设为 10。
  2. 连续两轮对话，验证第二轮能记住第一轮。
  3. 换一个用户，验证不会串数据。
  4. 加一个 clear 命令，调用 memory.clear()。
  5. 进阶：实现一个基于文件的 ChatMemoryStore，重启后恢复。
